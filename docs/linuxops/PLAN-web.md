# LinuxOps Web — план (CentOS 9)

Статус: **В РАБОТЕ** — ветка `feature/linuxops-web`, сделано до 0.6.0 включительно (Ф0–Ф4). План согласован 2026-11-17 (МСК).
Обновлён 2026-11-21 (МСК) под LinuxOps 0.3.53: RDP в настольном уже сделан (Ф6); добавлены «Версии ПО», CVE и «Обновить отмеченное». Ф4 сужен до входа в панель (решение 15).

## Цель
Веб-сервис на CentOS 9: всё, что умеет LinuxOps (действия по SSH, пользователи и sudo, прокси, обновления, «Версии ПО» с CVE и обновлением отмеченного, файлы, терминал, PowerShell и vSphere), плюс RDP. Управление — из браузера, через сервис. По сути зачаточный PAM:
- вход с MFA;
- права на хосты и действия;
- секреты не покидают сервер;
- аудит и запись сессий;
- что срочно закрыть по уязвимостям — по всему парку на одной странице.

Настольный LinuxOps остаётся (RDP в нём уже есть — 0.3.44–0.3.48).

## Архитектура

```
Браузер, внешние сервисы ──HTTPS/WSS──► nginx ──► LinuxOps.Web (ASP.NET Core, Kestrel, служба systemd)
                         ├─ LinuxOps.Core: SSH.NET, скрипты, план, каталог, PowerShell
                         ├─ SQLite: хосты, папки, роли, аудит, история
                         ├─ хранилище секретов: AES-GCM, мастер-ключ отдельно
                         ├─ вход: AD (LDAP) + второй фактор через API MK 2FA; локальные — свой TOTP
                         └─► guacd (127.0.0.1:4822) ──RDP/SSH──► хосты
                                └─ записи сессий → /var/lib/linuxops-web-rec (срок и предел объёма)
LinuxOps (WPF) ──► LinuxOps.Core  (+ вкладка RDP на mstscax)
```

- **Один сервер, одна ВМ.** SQLite хватит до десятков пользователей; кластер не нужен.
- **nginx перед Kestrel** (изменено 2026-11-21 на стенде): TLS и порт 443 — в nginx, Kestrel слушает только 127.0.0.1:5080. Так сервису не нужны права на порт 443, сертификат меняется без перезапуска сервиса, а адрес клиента приходит в `X-Forwarded-For` (верим только локальному прокси).
- **SSH-терминал и RDP — через `guacd`.** Запись сессий и их проигрывание работают одинаково для обоих. SFTP и действия — через наш `LinuxOps.Core`.
- **Интерфейс — Blazor Server.** Всё на C#, без сборки на Node. Терминал и RDP — готовая JS-библиотека `guacamole-common-js` через JS interop.

### Отложено (не в текущих этапах)
Решение 15 (владелец, 2026-11-21): вынесено из Ф4, вернуться позже.
- Подтверждение опасных действий вторым фактором (MK 2FA): «Применить», «Обновить отмеченное», перезапуск служб.
- Доступ на время (sudo или RDP на N часов) с автоснятием и согласование.
- Сертификат из «Настроек» (сейчас — меню `linuxops-web` на сервере).

Решение 16 (владелец, 2026-11-21):
- Ф7 — RDP и SSH настольного LinuxOps через сервис (WebView2 со страницей сессии, с записью). Веб и настольный клиент пока не совмещаем.
- В API (Ф8) — запуск действий, которые что-то меняют (применение и dry-run).

Решение 17 (владелец, 2026-11-22): в туду, сроков нет.
- **Браузер в панели** — веб-ресурсы (vCenter и любые другие) только через LinuxOps, с записью. Chromium в режиме киоска на сервере, картинка через guacd, как у терминала. На ресурс — свой список разрешённых адресов; загрузки и инструменты разработчика выключены политиками; на каждый сеанс — чистый профиль. Не Firefox; не RDP на Windows-сервер с браузером; не обратный прокси. Цена: на сервере графическая среда и xrdp или VNC, 300–500 МБ памяти на сеанс. Оценка ≈ 1,0.
- **RDP с токеном через настольный клиент** — токены (смарт-карты) в RDP, как в обычном виндовом RDP сейчас. guacd смарт-карты и USB не пробрасывает, поэтому: право выдаёт сервис, он же открывает разовый туннель до хоста, а настольный LinuxOps (`mstscax`) подключается через туннель. Потери: нет записи экрана и текста — остаётся только журнал «кто, куда, когда, сколько»; вход только из настольного клиента. Отдельное право «RDP с токеном (без записи)» на конкретные хосты, в аудите сеанс помечен «без записи».

Каждый этап сдаётся как версия, по обычному циклу:
- csproj и CURRENT;
- отчёт в `docs/agent_reports/`;
- проверка на стенде через браузер;
- сборка в `dist\LinuxOps.Web-<версия>`: скрипт проверяет уязвимые пакеты, свежесть .NET и суммы сторонних файлов (решение 18, с 0.7.2).

Когда начнётся код, у сервиса появятся свои `docs/linuxops-web/CURRENT.md` и `SKELETON.md`.

## Решения до старта
Ответы владельца — 2026-11-17.

1. **Пользователей — до 20 одновременно.** Роли нужны, Ф4 — в полном объёме. Что из этого следует:
   - **Блокировка хоста на время действия** — новое в Ф2, +0,2. Чтобы двое не ставили обновления на один хост сразу, второй видит «занят: кто, что, с какого времени».
   - **SQLite (WAL) хватает:** пишутся аудит и история, это единицы записей в секунду.
   - **Blazor Server:** 20 подключений — пустяк.
   - **Узкое место — `guacd`.** Сессия RDP с записью — это ~100–150 МБ памяти и заметный процессор на кодирование картинки.
   - **ВМ стенда** (до 2 подключений): 2 vCPU, 4 ГБ памяти, диск 40 ГБ одним томом.
   - **Боевой сервер** (20 человек), ориентир: 8 vCPU, 16 ГБ памяти, отдельный том 200 ГБ под записи сессий (`/var/lib/linuxops-web/recordings`), со сроком хранения.
   - **Нагрузка — в Ф3.** На стенде замеряем память и процессор одной сессии RDP и одной SSH с записью. Замер сделан в 0.6.0: на 20 RDP — от 4 vCPU и 8 ГБ (см. CURRENT 0.6.0). Полный прогон на 20 — уже на боевом сервере.
2. **На стенде входа нет.** Чтобы это не стало дырой:
   - firewalld пускает на 443 только адреса рабочих машин владельца;
   - вверху каждой страницы плашка «стенд без входа»;
   - в аудите вместо пользователя — адрес клиента.

   Вход (AD + второй фактор; RADIUS/LinOTP позже заменён на API MK 2FA — решение 11) переносится в Ф4 вместе с ролями. Сервис не используется вне лабы, пока Ф4 не сделан. Kerberos остаётся по желанию в Ф5.
3. **Стенд — новая ВМ AlmaLinux 10 в лабе**, создал владелец: 192.168.0.169, 2 vCPU, 4 ГБ, 40 ГБ, root по ключу.
4. **Цель для RDP — любая из двух лабораторных Windows** (контроллер домена или Exchange). Берём Exchange, чтобы контроллер лишний раз не трогать. RDP-сессия на сервере ничего не меняет.
5. **Сертификат — самоподписанный.** Внутреннего центра сертификации в лабе нет. Ставить AD CS на контроллер ради стенда не будем — это изменение лабы.

**Открыто (добавлено 2026-11-21) — решить до Ф2+:**

6. **Выход сервиса к базам уязвимостей** (Red Hat, NVD, CISA KEV, EPSS; только HTTPS 443). Наружу уходят имена пакетов, версии и номера CVE, не адреса хостов. Варианты:
   - прямо через корпоративный прокси со служебной учёткой — согласовать с ИБ;

7. **«Через сервер» для хостов без интернета** (бывший «через этот ПК»): хосты ходят в репозитории через прокси сервиса — тот же вопрос к ИБ, плюс что это видно в SIEM. Без согласования — только кэш хоста.
   - **Лаба — без согласования ИБ** (владелец, 2026-11-21): сервис ходит к базам CVE и репозиториям напрямую.

Процессоры подходят под обычную сборку (x86-64-v3): прод — Xeon Gold 5000-й серии, EVC не ниже Haswell; лаба — Ryzen 9 5900X, проверено на ВМ лабы. ## Риски
- **Сервис становится главной целью:** у него ключи root и пароли ко всему парку. Меры:
  - отдельная ВМ вне домена, наружу только 443;
  - MFA обязательно;
  - секреты не отдаются в браузер;
  - мастер-ключ хранится отдельно от базы;
  - аудит уходит в syslog, админ сервиса его не сотрёт.
- ~~**`guacd` на EL9**~~ — снят: в EPEL 10 есть guacd 1.6.0 с модулями SSH и RDP, на стенде запущен.
- **SELinux:** на стенде с 2026-11-22 enforcing, на боевом — тоже: nginx к Kestrel пускает `httpd_can_network_connect` (на стенде уже включён), guacd и записи сеансов проверены на enforcing в 0.6.0 (AVC нет; сервис и guacd — `unconfined_service_t`, метки ставит установщик).
- ~~**Записи сессий занимают диск**~~ — снят в 0.5.0: срок хранения и предел объёма в «Настройках», чистка раз в час.
- **RDP через `guacd` — без Remote Credential Guard и Restricted Admin**: их умеет только `mstscax` (настольный LinuxOps). В сервисе вход на Windows — своей доменной учёткой (NLA). Если RCG обязателен — RDP с ним только в настольном LinuxOps.
- **Сервис ходит наружу за базами CVE** — новый исходящий трафик с сервера с секретами. Только 443, только к четырём адресам, в аудите; при запрете — офлайн-зеркало (решение 6).
- **CVE — ложные тревоги:** Stream иногда закрывает уязвимость под другим номером сборки, чем RHEL; пакеты Debian / Ubuntu пока не сверяются. В сервисе — как в LinuxOps 0.3.53, с пометкой «не сверялось».
- **Вынос ядра (Ф1) задевает настольный LinuxOps.** Перед Ф2 — полный регресс приложения на лабе.
- **Проверка не автором** (правило §6) — отдельным агентом на каждом этапе. В оценке не учтена: +10–15%.
