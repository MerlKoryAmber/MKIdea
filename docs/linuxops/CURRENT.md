## 0.3.51
- **«Обновить отмеченное» прямо из таблицы «Версии ПО»** (по просьбе владельца).
  - **Галка — только у пакетов хоста, для которых есть обновление.** Контейнеры обновляются пересборкой образа, а собранное вручную — не пакетами, поэтому у них галок нет. «Отметить безопасности» отмечает обновления безопасности, а если таких нет — все обновления.
  - **Шаги:**
    1. **Предпросмотр** (`dnf upgrade --assumeno` / `apt-get -s install --only-upgrade` / `zypper update --dry-run`) — ничего не ставит.
    2. **Подтверждение** со списком пакетов. Если будет удаление пакетов — предупреждение.
    3. **Установка.**
    4. **Окно перезапуска** служб, у которых в памяти старые файлы. Отмечены службы наших продуктов (nginx, httpd, php-fpm, БД, redis, sshd); системные — по желанию.
    5. **Повторная проверка** версий этого хоста.
  - **Ставятся только отмеченные пакеты и пакеты той же сборки**, а не полный upgrade. Например, php-fpm тянет php-common, php-cli и остальные пакеты PHP, openssl — openssl-libs, чтобы версии не разошлись. Пакеты той же сборки ищутся по `SOURCERPM` / `source:Package`.
  - **Службы со старыми файлами** ищутся по `/proc/*/maps`: процесс держит удалённый файл из /usr, /lib, /bin, /sbin или /opt, а его служба берётся из `ps -o unit=`. Так работает везде, без `needs-restarting` / `needrestart`.
  - Перед перезапуском sshd выполняется `sshd -t`: при ошибке конфигурации sshd пропускается. Открытые сеансы SSH перезапуск не рвёт.
  - В окне перезапуска сначала идут службы продуктов (отмечены), затем системные — одним блоком без отметок. Пакеты RHEL для части служб перезапускают их сами (на лабе так сделали sshd и php-fpm), такие в список не попадают. После обновления openssl-libs старую библиотеку держат почти все системные службы — для них проще перезагрузка в окно обслуживания.
  - Галка «через этот ПК (туннель SSH)» у кнопки. По умолчанию — как получены списки в этой проверке. Тот же туннель, что в 0.3.50.
  - В History — предпросмотр (DRY-RUN), установка, перезапуск и повторная проверка.

## 0.3.50
- **«Версии ПО» больше не зависают без интернета** (вопрос владельца: долгая проверка). На лабе с недоступным прокси `dnf check-update` шёл 361 с — дольше тайм-аута действия (300 с), и не было даже таблицы версий.
  - **Сеть — не дольше 60 с.** dnf/yum — `timeout=10`, `retries=1`; apt — `Acquire::*::Timeout=10`; вся команда — под `timeout 60`.
  - **Не ответили — кэш хоста.** `dnf -C check-update`, имеющиеся списки apt, `zypper --no-refresh lu`. В «Деталях» — «Репозитории не ответили (…) — обновления по кэшу хоста от дд.мм.гггг чч:мм». Кэша нет — «обновления не проверены», таблица версий всё равно есть.
  - Дата списков пакетов показывается всегда («по репозиториям (dnf, списки от …)»). updateinfo — только по кэшу (`-C`): метаданные уже получены.
- **Галка «Списки обновлений — через этот ПК (туннель SSH)»** в окне параметров перед запуском. **По умолчанию выключена**, помнится до закрытия программы.
  - На ПК поднимается прокси на 127.0.0.1 (`PcProxy`), на хосте — обратный проброс SSH на случайный порт 127.0.0.1. dnf / apt / zypper получают этот прокси только на эту команду (`--setopt=proxy=`, `-o Acquire::http(s)::Proxy=`, переменные для zypper). Настройки хоста не меняются, проброс и прокси закрываются по окончании проверки. dnf с галкой — `--refresh`, иначе ответил бы по неустаревшему кэшу мимо туннеля.
  - Пускает только на порты 80 и 443. Дальше — системный прокси Windows / PAC. На запрос входа прокси — Negotiate / NTLM текущей учёткой Windows. Прокси с логином и паролем (Basic) не поддерживаются.
  - В «Деталях» — журнал: сколько соединений прошло через ПК и куда (например, `mirrors.centos.org:443 ×3`). Если соединений не было, так и пишется.
  - Сервер SSH запретил проброс (`AllowTcpForwarding no`) — «Туннель через этот ПК не поднят: …», дальше обычный путь.
  - **ИБ:** на время проверки хост ходит в интернет через ПК администратора. В журналах прокси этот трафик будет от его учётки. Туннель SSH (MITRE ATT&CK T1572) могут заметить SIEM / EDR. Включать по согласованию с ИБ — это написано и под галкой.
- Параметр действия может быть галкой (`ActionParam.Kind = "bool"`, значение «да» / «нет», пояснение — `Hint`).

## 0.3.49
- **Новое встроенное действие «Версии ПО: nginx, PHP… и контейнеры»** (по вопросу владельца про волну уязвимостей). Ничего не меняет на хостах.
  - **Что ищет:** nginx, Apache httpd, PHP и PHP-FPM (в т. ч. php8.x, remi), OpenSSL, OpenSSH, MySQL / MariaDB, PostgreSQL, Redis, Node.js, Java, Python — на хосте и **в работающих контейнерах docker и podman**: внутрь заходит та же проба (POSIX sh, через `exec`, только команды вида `nginx -v`). Контейнер без оболочки (distroless) — версии из переменных образа (`NGINX_VERSION`, `PHP_VERSION`…), затем из тега (`nginx:1.25.3`). Остановленные контейнеры — только счётчиком.
  - **Как оценивает.** Пакет хоста — по репозиторию: «обновление безопасности» (красный; dnf/yum — updateinfo, apt — репозиторий `-security`), «есть обновление» (жёлтый), «актуально в репозитории» (зелёный). Номер версии с последним у разработчика не сравнивается: дистрибутивы переносят исправления в старые номера (nginx 1.20.1 в RHEL 9 с заплатками) — иначе ложные тревоги. Закрытая у разработчика ветка у пакета — только пояснением. Контейнеры и собранное вручную — по сроку поддержки ветки: «без поддержки с …» (красный) / «поддерживается до …» / «нет данных».
  - **Сроки поддержки** — встроенные (PHP, nginx, Apache, OpenSSL, MySQL, MariaDB, PostgreSQL, Node.js, Python) на момент выпуска; поправить или дополнить — файлом `LinuxOps.eol.json` рядом с exe: `{"php": {"8.6": "2030-12-31"}, "nginx": {"1.32": null}}` (null — поддерживается, дата «гггг-мм-дд» или «гггг-мм»). Ошибка в файле — запись в `LinuxOps.crash.log`, используются встроенные.
  - **Вывод:** в «Деталях» таблица «Где / Продукт / Версия / Состояние / Откуда» (столбцы тянутся), сводка и строка о контейнерах; «Текст» — то же текстом (в History). Статус строки — WARN, если есть что обновить или ветка без поддержки.
  - dnf/apt обновляют только списки пакетов (как «Проверить обновления»); нет сети до репозитория — «обновления не проверены».
- Проверено на лабе через программу (CentOS Stream 9, podman, стенд 2FA — 10 контейнеров): хост — nginx 1.20.1 (актуально, ветка 1.20 закрыта у разработчика), httpd 2.4.62, PHP / PHP-FPM 8.0.30, OpenSSL 3.5.8, OpenSSH 9.9p1, Python 3.9.25 — с доступными обновлениями; контейнеры — PostgreSQL 16.15, Redis 7.4.10, nginx 1.30.7 (alpine, apk), OpenSSL 3.5.6 и Python 3.12.14 (Debian 13); 6 с. Разбор apt / zypper / переменных и тегов образа — на образцах вывода (на лабе их нет).

## 0.3.46
- **RDP: Remote Credential Guard больше не закрывает программу.** При подключении с RCG к доступному серверу LinuxOps падал через 1–2 с, с логином и паролем или без них. Причина: встроенный клиент (mstscax) показывает своё окно через `TaskDialogIndirect`, которая есть только в Common Controls 6, а у LinuxOps не было манифеста с этой зависимостью (процесс получал comctl32 5.82, исключение 0xC06D007F). Добавлен `app.manifest`: Common Controls 6 и, как прежде, `asInvoker`. В 0.3.44 RCG проверялся только при закрытом порте, поэтому падение не было замечено.
- **С RCG и Restricted Admin логин и пароль не спрашиваются.** Эти режимы входят на сервер текущей учёткой Windows через Kerberos, поэтому в окне подключения вместо полей — строка «Вход вашей учёткой Windows: ДОМЕН\логин». Если в Windows вход локальной учёткой — предупреждение, что так войти не получится. Сняли обе галочки — появляются поля логина и пароля. Галочки режима теперь вверху окна.
  - В строке сессии — та учётка, под которой вошли (раньше «текущая учётка Windows»).
  - В окне хоста Windows поле «Учётная запись для входа по паролю» — для режима без галочек.
- Сервер закрыл подключение до входа (Restricted Admin без Kerberos) — «Сервер закрыл подключение до входа» с подсказкой про Kerberos, а не «Сеанс на сервере завершён».
- Проверено через программу на dc-01 с этой (не доменной) машины: RCG — окно ошибки клиента (как у mstsc), после OK программа работает, статус с подсказкой; Restricted Admin — без падения, понятный статус; поля скрываются и появляются при переключении галочек; вход по паролю — сеанс открыт, отключение. Вход RCG / Restricted Admin на доменной машине — у владельца.

## 0.3.45
- **Испорченный `LinuxOps.defaults.json` больше не затирается.** Раньше, если файл не читался (ошибка в JSON после ручной правки, `null`, файл занят), программа молча стартовала пустой, а первое же сохранение (тема, план, Inventory) перезаписывало файл — хосты, папки и vCenter пропадали.
  - Ошибка в JSON → файл переименовывается в `LinuxOps.defaults.broken-<дата-время>.json` рядом с exe, программа начинает с чистого файла, при старте — окно «Файл настроек» с причиной (строка и позиция) и путём к копии.
  - Файл занят или нет прав (после 5 попыток за ~0,5 с) → окно с причиной, программа работает с пустыми настройками и **ничего не пишет** в файл до перезапуска.
  - Запись теперь через `LinuxOps.defaults.json.tmp` и подмену: оборванная запись не оставит полупустой файл.
- Проверено на копии программы: испорченный JSON и `null` — окно, копия совпадает с исходным файлом байт в байт, после смены темы создаётся новый файл, копия цела; занятый файл — окно, после освобождения и смены темы файл не перезаписан; исправный файл — окна нет, хосты сохраняются, `.tmp` не остаётся.

  - Причины ошибок — по-русски (порт закрыт, DNS, тайм-аут, неверный пароль); подсказка про Kerberos для RCG и Restricted Admin — только если до сервера достучались, а вход не прошёл.
- В Actions и SSH Files хосты Windows не показываются.
- Поставка: + WinForms (встраивание ActiveX), размер exe почти не изменился.
- Проверено через программу на dc-01 (лаба): обычный вход, размер по окну, полный экран и обратно, отключение и переподключение без окна, `/admin` + диски (в сеансе видны «C/D on <ПК>») + принтеры; RCG и Restricted Admin — понятная ошибка; регресс SSH на лабе. RCG и Restricted Admin на деле не проверены: с этой машины Kerberos к Merl.loc не работает (нет DNS домена).

## 0.3.43
- **«Добавить пользователя»: с ключом — sudo без пароля.** Раньше учётка с ключом и галочкой sudo попадала в группу `sudo` / `wheel`, и sudo спрашивал пароль пользователя, которого у учётки только с ключом нет вовсе (а у ключа и так своя парольная фраза). Теперь, если указан ключ, пишется `/etc/sudoers.d/linuxops-<логин>` с `NOPASSWD` (проверка `visudo -c`, при ошибке файл убирается); без ключа — как раньше, группа и пароль учётки. В итоге строки — «sudo без пароля добавлен».
- Уже созданной учётке достаточно запустить «Добавить пользователя» ещё раз с тем же логином и ключом — добавится файл sudoers, остальное не изменится.
- «Закрыть доступ» / «Открыть доступ» этот файл уже убирают и возвращают.
- Проверено на лабе настоящим скриптом: вход новым ключом, `sudo -n id -u` → 0; повтор — «уже есть»; без ключа с паролем — группа, `sudo -n` требует пароль; существующая учётка в группе + ключ — sudo без пароля. Тестовые учётки удалены.
